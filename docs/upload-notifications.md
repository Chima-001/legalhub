# Upload notifications: activate the sender, not another webhook

For the LegalHub project `iyeekpmutpugpmarddpa`, the capture trigger, private transport, one scheduled job and version 5 of the **existing** `notify-admins-on-upload` were installed. JWT verification stays on. Do not install another hook, the older pg_net version of 012, or a second mail function. The owner's frontend commit does not need to be pushed for the database to capture new pending uploads.

## Finish configuration privately

1. In Resend verify a domain you control and create a sending-only key for it. A DNS verification or provider account is an owner action; Supabase Auth SMTP is separate. The `onboarding@resend.dev` testing identity is not a production sender for your admins.
2. In the LegalHub Supabase Dashboard → **Edge Functions → Secrets**, save `RESEND_API_KEY` and `RESEND_FROM`. The latter is an address on that verified domain (optionally with the LegalHub display name). Never send these values, screenshots of keys or addresses to chat. No extra `UPLOAD_WEBHOOK_SECRET` is needed: signing and verification use the same key inside PostgreSQL.
3. **Save last**: in **Settings → API Keys → Legacy anon, service_role API keys**, copy this project's current **anon/public JWT** privately. In **Vault → Add secret** use name **`lh_upload_anon_jwt`**. Never choose the `service_role` key, a personal access token, `sb_secret_…`, a user session, or `sb_publishable_…`. If legacy anon JWTs are unavailable/disabled, stop; do not turn off JWT verification. Do not re-enable legacy keys or change project Auth settings casually. The ref and signer are already in Vault; do not rotate or export them for setup.

Adding the gate key is a **real cutover**: within the next scheduled minute the worker can process pending events captured **since this trigger went live**, not historical uploads that predate it. Do not create a test upload, real admin email or manual resend for verification. The provider key and verified domain cannot be manufactured by a Git installer. No SQL or redeploy is needed merely to add these three settings.

## One path from a committed upload to an email receipt

- One `AFTER INSERT` trigger on `public.materials` captures only a `pending` row and the admin IDs at that time. No network call runs in the upload transaction. A rollback leaves no event. Edits and approvals do not send alerts. No addresses, secrets or PDFs are sent by the browser.
- One private `pg_cron` job checks the committed outbox every minute, up to four ready events per pass. With no gateway setting it is idle. The private HTTP extension calls only the fixed project's existing Edge URL. Web roles cannot use its schema, read the outbox/Vault or run the privileged RPCs. A disposable privilege check found the hosted `pg_net` queue readable by web roles despite ordinary REVOKEs, so **pg_net was not left installed**. Do not relax those checks.
- The handler verifies a short-lived HMAC over the captured ID and timestamp via a service-only boolean RPC. It then rechecks each intended admin and their confirmed, active Auth email. Each accepted recipient has a durable provider receipt and a stable idempotency key; neither the owner-only appointment list nor a client-supplied address is used. Provider rejection, a missing sender, stale signature, wrong scope, lost role and empty audience are not successes. No different inbox is silently substituted.
- Temporary failures back off (2, 4, 8 … up to 60 minutes); the worker parks an event after 12 dispatch attempts or a nonretryable 4xx (except 408/429). The per-recipient 90-second lease and 23-hour ambiguous-send ceiling protect against duplicate provider sends. A successful HTTP status alone is not counted as mail. A working connection, a provider acceptance and inbox delivery are three different observations.

## Check without sending mail

Run `database/checks/upload-alert-health.sql` as operator. Expect **one** enabled AFTER INSERT, the expected capture function, one active scheduled job, private boundaries and the signer slots. The gateway-slot flag checks presence, not gateway acceptance. To validate its project/role/expiry locally inside the DB **without returning its value**, use only `SELECT count(*)=1 AS config_valid FROM legalhub_console.upload_hook_config();` after the gate is present. **Never `SELECT *` from that function.** The job's successful idle run does not mean mail was sent. After a naturally occurring upload compare captured events, waiting targets, last HTTP result and provider acceptances. Use Resend's delivery/bounce log privately for that natural message; acceptance is not inbox delivery. No actual admin contact is needed for fixtures.

If a pending event is parked, reconcile the cause with its existing per-recipient receipts and provider activity privately. Only an operator who intends a real delivery may retry **one previously captured event** via `legalhub_console.dispatch_upload_alert(the_material_uuid)`; accepted targets are skipped. Never reset the ledger, bulk replay, change the old audience or bypass the ambiguous-send ceiling. To pause sending but keep capture, an operator may deactivate **only** `legalhub_upload_dispatch` in Supabase Cron; resuming can send the waiting events. Keep private receipt retention and the Cron run-log cleanup policy under operator review.

## Restore/new-environment reference, not a live step

`database/ops/prepare-upload-notifier.sql` records the **project-specific** one-time transport setup. The revised `database/migrations/012-upload-alert.sql` installs capture and the job as one transaction and refuses a competing insert hook/job. For disaster recovery confirm project, backups, absence of another sender, extension ownership/ACLs, private Vault and verified sender first. Never point another environment at a production ref, bucket, domain or recipient. Deploy both notifier source files together and keep JWT on. A previous pg_net 012 is not auto-upgraded in place. Stop for a data-preserving migration if any different existing ledger is found. Moderation's 011 and Profile's 007 are independent releases: neither was needed to make this capture path work.
