# Academic calendar and annual levels — release notes

**Status: local milestone / staging candidate. Do not apply live SQL or publish this branch without separate approval.** Git does not install these migrations. A Live Server checkout can still point to production Supabase. Use the offline tests or an explicitly isolated staging backend for testing; do not create a live test account.

## Active calendar

- A signed-in student reads one public-to-members schedule. Administrators additionally see **Admin settings** in the homepage navigation. The static page is not a secret: it renders no editor until the server confirms the caller's current role. Every write checks the role again in the database using `auth.uid()` and the stored admin flag. No caller-selected UID, role, service key or client-side role claim authorizes a write.
- Set consecutive academic years (for example `2026/2027`), first or second semester, semester start, exam start and exam end. **Exam end is semester end**, inclusive. All school dates use **Africa/Lagos**, not the device's timezone. There is no fabricated initial schedule or invented exam end. An empty schedule, a failed read, a term not yet started, teaching, exams, the final day and a completed term have distinct displays.
- Publish the first calendar or replace the active dates with an exact typed confirmation. Changing any draft field clears the confirmation. The database checks the phrase, dates, role and expected revision; a stale editor must reload. There is one active row, no delete button and no term-history table. Students cannot write directly to the calendar table. A visible homepage reloads on a return to the tab and once per minute; it does not require a code edit to restart the countdown.

## Level rule approved for this transition

All pre-existing saved levels are levels **for 2025/2026**, irrespective of signup or last-edit time. Migration 007 adds a nullable `level_base_year` without a backfill; NULL means 2025. It sets a default for *future* inserts in a separate statement. It does not overwrite existing `current_level`, `level_updated_at`, identifiers or role flags.

The display advances one tier on each **7 November** at midnight in Lagos and stops at 500L. For example, a legacy 100L shows 100L on 6 November 2026, 200L on 7 November, still 200L on 1 December, and 300L on 7 November 2027. After the 2026 boundary has passed, eligible legacy students see the new level on the next read. Reading a profile, logging in, updating dates or starting a semester never writes a promotion. If `current_level` is absent, a recognised tier in the older library `level` column counts as the saved level. With neither, the old 100L display fallback stays 100L rather than inventing a promotion. Unrecognised `current_level` text is not silently reclassified.

New profiles and explicit profile corrections use the current November cycle **unless the immediately upcoming session has already been published**, in which case the upcoming session is used. This is how early entrants can select 100L before resumption: publish their upcoming session **before** they select it. The profile shows precisely which session a correction belongs to. A 100L assigned to 2026/2027 stays 100L at the 2026 boundary; its first advancement is 7 November 2027. Changing the calendar later does not retag any saved level. An arbitrary far-future schedule cannot assign levels multiple years ahead.

Corrections use an own-profile RPC with a server-derived identity/time, a matching reviewed account, an allowed tier, a matching assignment year and a typed confirmation. The existing `get_effective_level(p_uid uuid)` signature is retained and now respects the caller's profile RLS. The library reads it instead of the raw, unadvanced stored field. Explicit dashboard level and subsequent manual selections are not overwritten. Semester-default/dashboard/catalog changes are separate milestones.

## Controlled rollout (not authorization to execute)

1. Keep the release candidate local or on a non-deploying branch. Take a verified backup and arrange a short coordinated cutover. Inspect existing integrations that read/write profile levels, role grants, RLS, migration history and restore options. Resolve the separate signup rollout in `docs/signup-release-checklist.md`; never replay migrations 001–003 or the old review-kit draft. 006/007 require the reviewed profile permissions, including the earlier 004 restrictions. **Do not run 004 or 005 just to remove a preflight error.**
2. In a disposable environment first, review `006-academic-calendar.sql` and then `007-november-levels.sql`. Both are transactional with lock/statement timeouts. New object name collisions or preflight failures must be reviewed, not forced. 007 checks the audited December function body. It removes only browser direct UPDATE access to the three level fields; username/avatar editing remains. The old cached level editor cannot save via its old direct write after 007. Coordinate the frontend version and database release; do not silently relax grants to keep old writers working.
3. Exercise a student and admin, stale edits, the inclusive exam-end boundary, typed confirmations, the November date boundary, the 500L cap, updated profile/library reads and protected routes. An older database returns no new admin link; the new profile editor may show the old level read-only during staging. If the new RPCs are not visible to the staging API, verify the migration and refresh the PostgREST schema cache through the normal project process. Do not broaden permissions.
4. Only with explicit production approval for the project and each SQL scope: coordinate migrations and the frontend, have an authorized admin enter **real dates**, and verify member/admin behavior. Admin grants/revocations by email, owner protection across role-management interfaces, curricula and course management are not part of this patch. The owner's existing SQL-by-registration-number fail-safe has not been modified.
5. On a problem, stop writes/publishing and review rather than drop the new column or restore the old December formula blindly. After real corrections exist, their saved session anchors are needed. Do not delete user data, backfill all levels, change roles, or enable anonymous calendar writes as a rollback.
