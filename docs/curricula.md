# Curricula and courses

An administrator creates named curricula, not a new fixed level or semester. Each course listing belongs to the chosen curriculum and a specific level/semester; a curriculum can span any number of these slots. More than one curriculum can have courses in the same slot, including courses with the same display name. Each has its own ID and stable material key. Admins may reassign a course to another curriculum in its existing scope without breaking its links. Students cannot create or edit curricula.

**Using Settings:** open Curricula, enter the name, review the displayed phrase and add it. “Manage courses in this curriculum” filters Courses to it. Choose a level and semester, select “+ Add a course”, enter the details and confirm. An ordinary admin sees Term details, Curricula and Courses; only the owner or a designated delegator also sees Admin access. Only one heading can open, and all can close.

Renaming or deleting requires the exact action and current item name (for example `i delete Evidence`). Writes bind the current login, stable ID and reviewed revision. Adding/editing a course also checks the selected curriculum revision. Empty curricula and unreferenced courses can be permanently deleted. A curriculum with any assigned course (including archived) refuses deletion. Move the courses first. A course referenced by authored desk resources, case links or pending/approved materials refuses deletion; use Archive instead. A retired key is not reassigned to another course in the same slot. The first course with an available legacy display key keeps that key for old text-based materials; duplicates get distinct stable keys.

## Database review · not a step for applying the frontend patch

009 follows the separately reviewed single-owner 008. Recheck the target, backup and restoration plan first. Never install either to test a real user or publish fake curricula. If the existing course table is no longer empty or a constraint differs from the reviewed baseline, the transaction refuses: **keep the existing data and adapt the import; do not empty or drop anything to make it pass**. No SQL is run by the Git kit.

- Reuses existing `public.courses` IDs/name/code/level/semester; no duplicate course registry. Existing public read policy for those canonical fields remains. Archive is not a confidentiality control. Private tables hold the curriculum, extra listing metadata, audit and retired keys. Do not expose the private schema. Keep the eight confirmed 100L second courses unassigned until an admin explicitly assigns them. No new named curricula or example programmes are seeded.
- Replaces **only the course side** of the existing course–case FK with ON DELETE RESTRICT. Existing case rows/links and the case-side FK are untouched. Adds a nullable course FK on materials, filled by a trigger for new/changed, unambiguous assignments. No mass update to old books/files. General and historical text keys remain readable. New submissions for removed or exclusively archived keys are refused. Text references on legacy/unscoped records are checked conservatively before deleting a course.
- New catalogue writes are reviewed RPCs with private auditing and serialized membership checks. Existing SELECT and row-level material moderation/upload policies are preserved; no R2/edge function changes. Removes direct course write grants and non-row privileges (including TRUNCATE) on the three catalogue/dependency tables from public web roles. Verify other operator integrations before approval; abort on inherited write privileges outside the reviewed baseline.
- Coordinate a later frontend release with the DB rollout. Until 009 is installed the new catalogue readers report unavailable; don't deploy the new consumer code first. ## Tests

From the root, with the existing locked `tests/auth` PGlite dependency: `node tests/admin/authority-smoke.mjs` and `node tests/admin/curricula-smoke.mjs`. The suites create fresh, single-connection, in-memory PostgreSQL databases and synthetic users. `node --test tests/admin/catalog.test.mjs` covers shared readers as well. These are not live deployment or multi-connection load tests. Upload success text, plain Home→Library semester defaults, moderation dialogs, 007 rollout and offline reading are separate milestones.
