# Admin access · separate from publishing a calendar

Members cannot open Admin settings. The owner and privately designated administrators may review a **single registered, active, verified Auth email** and explicitly grant or revoke admin access. Ordinary administrators cannot delegate. Granting admin does not designate a manager. Demoting a non-owner manager removes their designation in the same transaction; a later regrant does not restore it. No web designation, user-directory search or membership deletion. The other tools have their own server checks. Opening or closing a heading never saves anything.

008-admin-authority.sql is a **new, separately reviewed** migration, not the older admin-workspace draft. Do not execute it to preview the UI. It checks the profile/identity schema and privileges, and aborts atomically unless the operator has deliberately supplied a privately verified owner UUID, official registration number and current confirmed email. The binding is a single stable UUID, not an editable profile claim. The binding restricts deletion of both the owner’s profile and Auth row. It does not create or promote an account. The intended registration is the owner's previously supplied official record: verify against the trusted school/operator record, not a student-provided field alone. Do not commit any real identity values.

For a separately approved live rollout, review restorable backup, actual SQL recovery operator, all app/service callers, profile grants and pre-existing triggers first. In the **same private SQL Editor transaction** after BEGIN and before the binding block, the owner can set `legalhub.install_owner_uuid`, `legalhub.install_owner_reg`, and `legalhub.install_owner_email` with transaction-local `set_config(..., true)` using their verified values. These inputs are used only during installation. A blank or mismatched binding refuses installation. Roles removed from the web require a transaction-bound reviewed change. Direct, no-request-identity SQL by the trusted migration owner retains the official-registration-number workflow, including a deliberate change to their own admin flag. Protect SQL Editor and service credentials: a DB role is not proof of which human holds its credentials. Keep the private schema out of exposed API schemas. Designations of additional already-verified admins are separate owner/operator actions, never made by this migration; verify current admin, lock the profile and the role-change advisory lock in the same operator transaction.

Local test only: `node tests/admin/authority-smoke.mjs` uses the existing pinned PGlite dependency under tests/auth and synthetic registration numbers. Never test an actual grant/revoke in the one live database, even from a local frontend.

## Admins you added · owner only (010)

On the real Admin settings page, open **Admin access → Admins you added**. The list contains current, confirmed Auth email addresses, sorted alphabetically, for the bound owner’s own active appointments. It has no names, registration numbers, IDs or controls for other accounts. It loads only for the owner while the card is open. A successful grant/revoke refreshes it; **Refresh list** picks up changes from another session. Failed reads are not displayed as empty lists. Closing the card, hiding/leaving the page or changing accounts clears the emails, including any late response. Nothing is saved to browser storage.

`010-owner-admin-emails.sql` is incremental. It does not bind another owner, appoint anyone, change the grant/revoke routine, or reinstall 008/009. The authenticated RPC compares `auth.uid()` both to the caller’s expected account and to the private owner binding and requires active owner admin access. The `owner` capability is only a UI hint; the `roles` flag alone is **not** owner authorization. A designated manager can still review an exact email but cannot retrieve this list. Do not expose the private console schema or share privileged database credentials.

The one-time import uses the latest recorded 008 grant/revoke **across all actors**, the still-active role and the bound owner. Attribution is not guessed: pre-existing admins with no owner grant, the owner, later delegate grants, revocations and ambiguous tied events are not imported. For history before 010, unrecorded SQL changes cannot be reconstructed from the 008 audit. Going forward, a role transition ends the previous attribution and only a fresh owner-authored reviewed grant creates one. A direct SQL recovery/regrant is not counted as a web appointment by the owner. The private table stores only grant references, not a second admin flag or a copy of any email. Deleting an attribution does not delete the account.

Synthetic regression checks: `node --test tests/admin/back.test.mjs` and `node tests/admin/owner-emails-smoke.mjs` (existing local PGlite test dependency). No test account belongs in the live project.
